# Paid x402 resources

The release app supports public HTTPS x402 v2 services using exact USDC
EIP-3009 payments on Base mainnet (`eip155:8453`). It uses Circle's native Base
USDC contract, `0x833589fcd6edb6e08f4c7c32d4f71b54bda02913`, with six decimals
and EIP-712 domain `USD Coin`, version `2`. Other tokens, chains, Permit2,
ERC-7710 and variable-price payment schemes are not supported.

This is a specialised chat payment route. The Wallet screen separately supports
ETH/USDC transfers on Base and Ethereum; chat does not expose general transfers
or arbitrary contract calls. See [the capability table](usage.md#evm-capabilities-by-entry-point).

## Using a service

Read a service's documentation with ordinary web retrieval first; Markdown is
returned as bounded untrusted text. Use `x402.request` discovery with the
published Bazaar JSON endpoint, rather than the documentation URL. A failed
request does not establish that the service is offline or that payment support
is absent.

Provide the exact resource or Bazaar discovery URL. Minutus can discover bounded
Bazaar JSON POST resources, collect their required input and prepare the request.
A bodyless protected GET can be purchased directly. Discovery metadata and model
prose are untrusted; the live HTTP 402 challenge supplies the payment terms.

Before any public request, native review displays its complete URL and JSON
body. Invisible and directional formatting characters are shown as JSON escapes
so they cannot conceal or reorder the review text; the transmitted body is unchanged. The unpaid request may already create a quote or pending order at the
service. A separate payment review shows the exact price, network, USDC contract,
payer, recipient, signed authorisation expiry and local approval expiry. Signed
authorisations expire at the earlier of the merchant deadline or two minutes
after preparation. The merchant can submit an issued authorisation until that
signed expiry; cancelling a local request cannot recall a signature already sent.
Signing requires fresh app-password authentication.
Discovery, outbound-request approval and payment approval are distinct steps.

The host freezes the method, URL and body across the unpaid request and one paid
retry. Public DNS answers are checked and connections pinned; redirects, ambient
credentials, cookies, proxies and automatic transport retries are disabled.
An approved signature is attached only to that exact request. Changed requests,
expired approvals, revoked wallet readiness and already-consumed approvals fail
closed. Local request cancellation is checked again after password entry.

## Limits and failures

- The live challenge must offer exactly one supported payment requirement.
- Bazaar input uses the app's bounded JSON Schema subset and a maximum 32 KiB
  JSON-object request body. This is not a general authenticated HTTP client.
- Unknown protocol extensions and unsupported Bazaar schema features are rejected.
- Delivered content is bounded static JSON, text or extracted HTML. Model results
  retain the content type, source URL/hash and extraction truncation flags.
  `contentComplete` describes extraction limits, not merchant fulfilment.
  Shortened JSON is a text fragment and must not be treated as a complete result.
  Binary file
  delivery and arbitrary browser interactions are not provided by this adapter.
- Settlement receipts are checked against the candidate's network and payer.
  This is protocol validation, not independent on-chain confirmation.
- A timeout, malformed receipt or connection loss after submission can leave an
  uncertain payment outcome. No automatic second payment is attempted. Check
  the existing transaction or merchant order before considering another request.
- Successful settlement can still be followed by unavailable or unusable content.
  That does not make a second payment safe.

## Development qualification

The localhost qualification transport remains debug-only. In debug builds,
`ZETA_X402_DEBUG_BASE_URL` selects an explicitly scoped HTTP loopback subtree
and Base Sepolia testnet instead of the public transport. Release builds exclude
that transport and ignore this setting. The public path uses Base mainnet.
The lower-level payment library also retains public HTTPS Base Sepolia admission
for synthetic and testnet qualification.

Automated tests cover mainnet policy/domain binding, request identity and body
preservation, native review content, final submission revocation, single-use
approvals, cancellation and settlement failures. A dedicated release-binary check verifies that the public adapter is advertised,
accepts public HTTPS, and rejects loopback even with inherited debug configuration.
It exits before app-data access, network requests or signing.
These checks do not constitute a real-money purchase or a live merchant
qualification; no such purchase is performed by the automated checks.
